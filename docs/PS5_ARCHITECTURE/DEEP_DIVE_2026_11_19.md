## Critical new findings

### 1. GPU replay must be a correctness gate, not a feature demo

Prosper [ADR 0005](https://github.com/mattias800/prosper/blob/main/prosper/docs/adr/0005-replay-gate-for-gpu-changes.md) proposes gating GPU PRs on local replay hashes against a baseline. **Status is proposed**, not a verified deployed policy. Their captured frames may contain copyrighted imagery and cannot be put into public CI; hosted CI's software GPU differs from real RADV. For NEXORA, build synthetic GPU fixtures suitable for public CI and keep private captures local. Verify packet order, final pixel hashes and fence semantics separately.

### 2. HLE coverage must not confuse a stub with a working implementation

Prosper [ADR 0007](https://github.com/mattias800/prosper/blob/main/prosper/docs/adr/0007-generated-hle-coverage.md) identifies a serious false-success case: an unimplemented HLE call returning zero can be mistaken for successful execution. **Status proposed.** NEXORA should classify imports as resolved-to-implementation, explicit unsupported, unresolved and title-provided; simply finding a symbol is not proof of implementation. Build the report from actual loader/registry metadata rather than grepping source.

### 3. Vulkan fence waits may be a major source of CPU/GPU underutilization

Prosper [ADR 0009](https://github.com/mattias800/prosper/blob/main/prosper/docs/adr/0009-pipelined-gpu-submission.md) reports a measured 5.03-second gameplay sample with **1,175 ms** of executor-thread waiting and GPU 5–15% busy. Its authors found graphics-batch waits a bigger opportunity than compute-dispatch waits, and describe a staged deferred-wait design. These are **Prosper-specific numbers, not NEXORA measurements**. Before attempting async GPU submission in NEXORA, measure wait time by reason, guest-visible observation points, fence retirement order and GPU timestamps. Avoid unsafe unconditional wait removal.

### 4. Shader binary round-trip fixtures

[opengnm-psbc](https://github.com/PS4-OpenGNM/opengnm-psbc) documents SPIR-V → NIR → ACO → PS4/PS5 shader binary output, including eight shader stages and GFX10.3 target. Its README claims a PS4 hardware validation, **not a complete PS5 hardware validation**. Combine its self-authored test shader artifacts with NEXORA's RDNA2 decoder in offline tests, subject to license and artifact provenance. [OpenGNM shader binary reference](https://github.com/PS4-OpenGNM/opengnm/blob/main/docs/reference/shaderbinary.md) documents `Shdr` and `OrbShdr` signatures and stage IDs; keep PS4 GNM and PS5 AGC format assumptions separate.

### 5. Vulkan command coverage needs explicit refusal

[PS5_Vulkan testing](https://github.com/mihawk-99/PS5_Vulkan/blob/main/docs/TESTING.md) uses a command audit that requires each exposed Vulkan command to be implemented, explicitly refused, or supplied by runtime. For NEXORA, build a table of translated GPU commands and unsupported variants, failing deterministic tests when silent fallbacks mask missing functionality. Host unit tests and real hardware evidence are different confidence levels.

### 6. Synthetic PS5 linkage tests

[ps5link-sdk](https://github.com/Rufidj/ps5link-sdk/blob/master/README.md) documents SCE dynamic linking, NID imports, PLT/GOT and shader assembly. Its authors report PS5 firmware 9.00 testing. NEXORA can create its **own** synthetic relocation/import fixtures rather than relying on copyrighted titles or proprietary SDK material.

### 7. ps5rs and shadPS4: narrower claims

The inspected `ps5rs/crates/ps5-shader/README.md` contains only a heading; it does **not** establish shader compiler correctness or coverage. Deeper source inspection is required. shadPS4 is a PS4-focused reference; it is not direct proof of PS5 GPU/HLE behavior.

Other repositories may have mixed dependencies and file licenses. No proprietary firmware, decrypted game files, Sony SDK material or keys were collected.
